# library — 현재 범위와 진행 상태

정리일: 2026-09-07. [공통 학습 기록](../../LEARNING_DIRECTION.md)과 최신 사용자 요청을 함께 확인해.
옛 SPEC는 [원문 보관본](../../learning/history/library-spec-before-preparation.md)에 남겼어.

## 목적

도서관의 기능 수를 늘리는 것보다, 하나의 대출 흐름을 사용자가 직접 설계·구현·검증하고 다른 요구에 적용하는 경험을 만든다. 이 프로젝트가 최종 포트폴리오여야 한다는 합의는 없다.

## 현재 설정과 증거

- 소스 설정: Java 21, Spring Boot 4.1.1, Gradle, JPA, Validation, Lombok, H2와 MySQL 드라이버.
- 도서 등록·단건·전체 조회는 사용자 수동 실행 결과를 확인했다. 정상 등록 201, 빈 제목 400, 조회 200, 없는 도서 404.
- 이번 자료 정리에서 서버나 자동 테스트를 실행하지 않았다. 새 매핑의 저장 결과는 아직 미검증이다.
- 자동 테스트 소스는 contextLoads 한 개이며, 이것만으로 도서·대출 기능을 검증했다고 판단하지 않는다.

## 현재 대출 정책

- 한 회원의 한 대출은 여러 권을 묶는다. 이미 대출 중인 도서는 새로 빌릴 수 없다.
- 대출일과 14일 뒤의 반납예정일을 대출에 기록한다. 날짜 단위로 LocalDate를 사용한다.
- 한 권씩 반납할 수 있다. 실제 반납일은 개별 대출도서에 기록한다.
- 전체 반납은 아직 반납하지 않은 항목들을 반납 처리한다. 전체 실제 반납일을 따로 저장하지 않는다.
- 기록 생성과 도서 상태 변경은 한 작업으로 함께 성공하거나 롤백해야 한다. 동시 요청 안전성은 별도 검증 대상이다.
- 도서와 회원의 존재, 같은 요청 안의 중복 도서, 빈 대출 목록 등 입력 정책은 실제 대출 작업을 시작할 때 완료 조건으로 구체화한다. 현재 구현 완료로 보지 않는다.

## 엔티티 4개

| 엔티티 | 한 객체의 의미 | 현재 필드 |
|---|---|---|
| Book | 현재 스키마에서 대출 상태를 가진 도서 한 개 | id, name, author, isbn(유니크), isUsed, loanItems |
| Member | 대출하는 회원 | id, name, loans |
| Loan | 한 회원이 한 번에 빌린 묶음 | id, member, loanItems, loanDate, dueDate |
| LoanItem | 특정 대출에 포함된 책 한 권의 기록 | id, loan, book, returnedDate |

관계는 Member 1:N Loan, Loan 1:N LoanItem, Book 1:N LoanItem이다. LoanItem이 Book과 Loan을 연결한다.

Book에 ISBN 유니크 제약을 둔 상태에서 같은 ISBN의 실물 여러 권을 표현하는 문제는 아직 다루지 않았다. 별도 실물 엔티티 도입을 지금 확정하거나 과제로 추가하지 않는다.

## API 상태

| 경로 | 상태 |
|---|---|
| POST /books | 코드 있음, 사용자 정상/빈 제목 요청 확인 |
| GET /books/{id} | 코드 있음, 사용자 존재/미존재 요청 확인 |
| GET /books | 코드 있음, 사용자 빈/비어 있지 않은 목록 확인 |
| 회원·대출·반납 API | 아직 없음. 여러 권 입력과 개별 반납에 맞는 계약은 구현 단계에서 정함 |

## 현재 과제와 후속 범위

현재: Loan의 회원·기준 날짜를 받는 생성자, 14일 반납예정일 계산, JPA용 기본 생성자.

그다음 후보는 관계를 연결하는 생성 흐름, 저장·재조회, 여러 변경의 원자성, 개별 반납이다. 한 번에 하나의 목표와 완료 조건으로 진행한다. 회원 CRUD 전체를 먼저 완성할 의무는 없다.

이전 계획의 5권 한도, 연체 목록, MySQL 전환은 후속 후보로 보존한다. 이메일/가입일시/대출상태 enum, 전체 반납 API의 구체 경로도 현재 필수 구현으로 되살리지 않는다.

## 입력·응답 변환 결정

현재 BookService는 제목·저자·ISBN 개별 파라미터를 받고, ResponseBook(Book) 생성자로 응답 변환을 모은다. Command/정적 from/별도 Mapper는 필수가 아니며, 새 요구에서 실제 이점과 비용이 생기면 재검토할 수 있다.

‘안 써본 쪽을 선택’, ‘계층이 섞이면 무조건 탈락’, ‘재논의 금지’라는 옛 문구는 현재 기준으로 사용하지 않는다.
