# 혼자 진행할 수 있는 범위를 확인하는 과제은행

작성 기준: 2026-09-07의 library 소스와 학습 대화. 현재 구현이 바뀌면 과제를 시작할 때 다시 확인해.

**이 문서는 일곱 개를 전부 구현하라는 숙제가 아니야.** 다음 대화에서 하나만 골라 사용하려고 준비한 과제은행이야. 지금 안내받은 `Loan` 생성자 작업도 이 문서 때문에 자동으로 바뀌지 않아.

목표는 점수나 속도가 아니라, 요구사항을 받았을 때 **어디까지 혼자 진행하고 어느 지점에서 도움이 필요한지** 확인하는 거야. 외운 설명을 잘하는 것과 직접 구현·검증하는 것은 따로 기록해. 이 결과는 채용 합격 여부나 개발자 자질을 판정하는 기준이 아니야.

## 처음 사용할 때

첫 진단은 **D1 하나**, 참고 시간은 30~45분이 좋아. 제한시험이 아니므로 시간이 더 필요해도 괜찮아. 도서 요청 흐름을 이미 혼자 추적한 최근 증거가 있다면 반복하지 않고 D2 또는 D5의 설계 부분으로 넘어갈 수 있어. 한 번에 새로운 과제는 하나만 진행해.

기존 코드와 공식 문서는 자유롭게 찾아봐도 돼. 모르는 문법을 찾아보는 건 정상적인 개발 활동이야. 막히면 [해당 미션의 힌트](support/02-hints.md) 중 1단계만 먼저 열어봐. 도움을 받아 완성했어도 그 시도는 학습 성과로 남기되, 혼자 완성한 것으로 적지는 않아.

답변은 아래 다섯 줄부터 시작하면 돼. 긴 보고서를 쓸 필요는 없어.

```text
미션 / 오늘 다룰 범위:
내가 이해한 요구사항:
찾은 코드 또는 변경 후보와 이유:
확인한 결과 / 아직 확인하지 못한 것:
사용한 도움 / 구체적으로 막힌 한 지점:
```

튜터는 답을 보고 다음 도움을 정해. 아직 이해가 확인되지 않았는데 클래스를 늘리거나 일곱 과제를 연속으로 지시하지 않아. 풀이 후 확인할 [리뷰 가이드](support/02-review-guide.md)는 별도 파일에 있어.

## D1. 없는 도서를 조회한 요청은 어디를 지나갈까?

**첫 범위: 실행 관찰과 변경 계획만. 기능 코드를 수정하지 않아도 돼.**

현재 도서 조회에서, 없는 도서라는 사실을 앱 화면에서 구분해 보여주려 한다고 해보자. 요청 계약을 다음처럼 바꾸자는 제안이 들어왔어.

- 존재하는 도서의 조회 응답은 그대로 둔다.
- 존재하지 않는 숫자 ID로 조회하면 상태 코드는 유지하고, 본문을 `code`와 `message`가 있는 JSON으로 제공한다.
- 이 실패의 `code` 값은 `BOOK_NOT_FOUND`다.
- 잘못된 형식의 ID가 같은 실패인지도 확인해야 한다.

네가 할 일:

1. 직접 등록해서 얻은 ID, 존재하지 않는 숫자 ID, `abc`를 각각 `GET /books/{id}`에 넣기 전에 예상 결과를 적어봐.
2. 응답 상태·본문·가능하면 Content-Type을 확인해. 데이터가 없거나 서버 실행이 막히면 그 사실도 구분해서 적어.
3. 존재하지 않는 숫자 ID 요청을 실제 소스에서 따라가며, 어디서 실패가 생기고 어디서 응답이 되는지 찾아봐.
4. 위 제안을 구현하려면 어느 파일을 바꿀지와 이유를 적어봐. 새 파일을 만들고 싶다면 그 책임을 한 문장으로 설명해.

**완료 증거:** 실제 응답 또는 실행 장애의 구체적 기록, 따라간 파일·메서드, 요구사항과 연결되는 변경 계획. 파일 이름만 나열하거나 상태 코드를 맞힌 것만으로 완료하지 않아.

이 미션은 코드 읽기 진단이야. 여기서 잘했다고 대출을 독립적으로 구현할 수 있다고 판단하지 않아.

## D2. 같은 사건을 업무 기록과 DB 기록으로 표현해보기

**첫 범위: 설명과 그림 또는 표만. 매핑을 다시 전부 작성하는 과제가 아니야.**

다음 사건을 기록하려고 해.

- 회원 민지는 9월 7일 책 A와 책 B를 함께 빌렸다.
- 민지는 9월 8일 책 C를 추가로 빌렸다.
- 민지는 9월 9일 책 A만 반납했다.
- 회원 준호는 9월 10일 반납된 책 A를 빌렸다.
- 한 번에 빌린 묶음의 대출일과 14일 뒤 반납예정일을 남기고, 책별 실제 반납일도 남긴다.

각 이름이 무엇을 뜻하는지 네 말로 먼저 적어봐: 회원 한 명, 물리적인 책 한 권, 대출 한 번, 그 대출에 포함된 책 한 권의 기록. 이름이 섞이면 애노테이션을 먼저 고치지 말고 이 정의부터 비교해.

네가 할 일:

1. 사건이 끝난 뒤 어떤 기록이 몇 개 있어야 하는지 적어봐. 실제 번호 대신 임시 ID를 사용해도 돼.
2. 과거 대출과 새 대출이 같은 책을 어떻게 구분해서 참조하는지 그려봐.
3. 현재 네 엔티티 네 개를 읽고, 방금 그린 기록과 코드가 대응하는지 확인해.
4. `Member.java`의 대출 목록 매핑 하나를 골라, 목록 원소 타입·`mappedBy` 문자열·상대 파일의 필드·DB 컬럼을 서로 구분해서 설명해. 한 줄에 다른 파일 이야기를 섞지 않아도 돼.

**완료 증거:** 네가 먼저 만든 사건 기록, 실제 코드와 일치/불일치하는 위치, DB에 어떤 연결 값이 필요하다는 설명. 아직 저장 동작이 없으면 실행 검증은 ‘아직 안 함’으로 남겨.

## D3. 여러 권을 한 번에 빌릴 때 일부만 저장되지 않게 하기

**향후 구현 과제야. 현재 소스에는 대출 서비스와 저장소, 생성 동작이 준비돼 있지 않아.** 지금 곧바로 요청을 보내라고 지시하는 문서가 아니야. 선택한 날에는 먼저 요구사항을 처리 순서로 적고, 그다음 한 번에 구현할 범위를 정해.

이 미션을 선택했을 때 사용할 연습 정책:

- 기존 회원 ID, 빌릴 도서 ID 목록, 기준 날짜를 입력으로 받는다.
- 목록은 비어 있을 수 없고, 같은 도서 ID가 두 번 있으면 요청 전체를 거절한다.
- 회원이나 책 하나라도 없거나, 책 하나라도 이미 대출 중이면 요청 전체를 거절한다.
- 성공하면 한 번에 빌린 기록과 각 책의 기록을 남기고, 대상 책들은 대출 중이 된다.
- 반납예정일은 기준 날짜의 14일 뒤다. 반납 전 실제 반납일은 비어 있다.
- 작업 도중 실패하면 이 요청으로 인한 기록과 도서 상태 변경이 모두 남지 않아야 한다.

빈 목록·중복 ID 처리 등은 이 진단을 위한 제안 정책이야. 사용자와 이미 합의된 전체 서비스 정책인 것처럼 기존 문서에 소급하지 않아.

첫 제출물은 처리 순서, 읽을 데이터와 바꿀 데이터, 실패 지점, 수정할 곳의 후보야. 그 계획을 리뷰한 뒤 구현해. 회원 가입·로그인·프런트엔드 전체를 만들 필요는 없고, 기존 회원·도서는 테스트 준비 데이터로 사용할 수 있어. 서비스 동작부터 확인해도 돼.

**완료 증거:** 두 권 정상 대출, 일부 부적격 요청, 저장 과정 실패 각각의 실행 결과와 요청 전후 DB 상태. 단순히 예외가 발생했다는 사실만으로 저장 상태까지 검증했다고 적지 않아. 이 단계에서 동시 요청 안전성을 검증한 것으로 보지는 않아.

## D4. 한 권을 반납하고 같은 요청이 다시 도착했을 때

**D3 이후의 별도 미션이야. 대출과 동시에 구현하도록 묶지 않아.**

연습 정책:

- 선택한 대출도서 기록 하나를 반납할 수 있다.
- 같이 빌린 나머지 책은 대출 중 상태를 유지한다.
- 해당 기록에 실제 반납일을 남기고 그 책을 다시 빌릴 수 있게 한다.
- 같은 기록의 반납 요청이 다시 오면 첫 반납일을 유지한 채 성공 처리한다.
- 없는 대출도서 기록을 지정하면 실패한다.
- 대출일보다 앞선 날짜로 첫 반납을 처리할 수는 없다.

여기서 재요청을 성공 처리한다는 것은 이 미션의 계약이야. 현재 프로젝트에 이미 구현돼 있다는 뜻은 아니야.

다음 순서를 네 구현에서 재현해봐.

1. 민지가 A와 B를 빌린다.
2. 민지가 A만 반납한다.
3. 준호가 A를 새로 빌린다.
4. 민지의 예전 A 반납 요청이 다시 들어온다.

4번까지 끝난 뒤 각 기록과 현재 도서 상태가 어떻게 남아야 하는지 **실행 전에 네가 적어봐.** 그 예상과 실제 저장 결과를 비교해.

**완료 증거:** 첫 반납, 부분 반납, 재요청의 상태 기록과 이를 지키는 검증. 대출 전체의 날짜 하나만 보고 결론 내리지 말고 개별 기록도 확인해.

## D5. 다른 업무에서도 직접 모델을 정할 수 있을까?

**도서관과 다른 ‘동아리 행사 참가 신청’ 연습이야. 처음에는 모델과 처리 흐름만 작성해.** 새 Spring 프로젝트 전체를 즉시 만드는 과제가 아니야.

요구사항:

- 행사는 여러 번 열리며 각 행사는 정원이 있다.
- 한 회원은 여러 행사에 신청할 수 있다.
- 같은 행사에 같은 회원의 유효한 신청은 하나만 존재한다.
- 신청을 취소하면 다른 사람이 신청할 자리가 생긴다.
- 신청 시점과 취소 시점을 기록하고, 취소한 과거 기록도 남긴다.
- 취소했던 회원이 같은 행사에 다시 신청할 수 있다.
- 우선 요청이 순서대로 들어오는 경우를 다룬다.

네가 할 일:

1. 도서관 클래스 이름을 먼저 바꾸지 말고, 이 업무에서 보관할 사실과 지켜야 할 규칙을 적어봐.
2. 정원 1인 행사에 민지 신청 → 준호 신청 시도 → 민지 취소 → 준호 신청이라는 순서를 표현해.
3. 객체와 데이터의 관계, 취소 후 재신청 기록을 보관하는 방법을 제안해.
4. 그중 신청 가능 여부와 상태 변경의 핵심 부분 하나를 골라 Java 코드와 작은 검증으로 구현할 범위를 정해봐. 구현은 계획 리뷰 후 별도 세션으로 이어가도 돼.

**설계 단계 증거:** 직접 정의한 모델, 기록 예시, 처리 순서. **구현 단계 증거:** 직접 작성한 핵심 동작과 예상 결과를 확인한 테스트. 설계만 했으면 ‘설계 확인’으로 기록하고 구현까지 완료한 것으로 보지는 않아.

## D6. 남은 한 자리에 두 요청이 동시에 들어오면

**후반 선택 미션이야. D5의 신청 기능을 DB까지 연결하고, 순차 실행을 검증한 뒤에 사용해.** 현재 library 코드에 이미 동시성 결함이 있다고 판정한 과제가 아니야.

- 정원이 1이고 유효한 신청이 없는 행사에 서로 다른 두 회원이 동시에 신청한다.
- 끝난 뒤 유효한 신청은 정확히 하나여야 한다.
- 두 호출이 모두 성공했다고 응답해서는 안 된다.
- 실패한 호출이 유효한 신청 기록이나 정원 변경을 남겨서는 안 된다.

먼저 두 요청의 읽기와 쓰기가 겹치는 순서를 적어봐. 현재 구현이 이 조건을 지키는지 재현하고, 지키지 못한다면 대안과 비용을 비교한 뒤 하나를 적용해. 사용할 기술 이름은 정해두지 않았어.

**완료 증거:** 실제 동시 실행을 만든 방법, 실행 환경과 DB 종류, 두 요청 결과, 종료 후 저장 상태, 선택한 해결 방식이 규칙을 지키는 이유. 한 번 우연히 성공하거나 순서대로 두 번 호출한 것은 동시성 검증으로 보지 않아.

## D7. SQL을 보고 조회 변경의 효과를 설명하기

**대출 저장과 조회가 가능해진 뒤의 선택 미션이야. 지금 `findBooks()`에 성능 문제가 있다고 가정하지 않아.**

새 조회 요구사항:

- 특정 회원의 최근 대출 10건을 최신순으로 보여준다.
- 각 대출의 대출일, 반납예정일, 포함된 책 제목, 개별 반납 여부를 보여준다.
- 책이 여러 권 있어도 결과의 대출 한 건이 여러 건처럼 중복되면 안 된다.
- 대출일이 같은 기록들의 순서도 반복 조회에서 안정적이어야 한다.

먼저 필요한 응답과 데이터를 정하고 동작하는 조회를 만들어. 이후 대출 기록이 1건일 때와 20건일 때 실제 SQL·반환 결과를 비교해. 개선이 필요하다고 판단한 부분 하나만 바꾸고 같은 조건에서 다시 확인해.

**완료 증거:** 데이터 수, DB와 실행 조건, 실행 SQL 또는 SQL 수 집계, 응답의 정확성, 개선 전후 비교. 개선할 이유를 찾지 못했다면 측정 근거와 함께 그대로 둬도 돼. ‘더 고급인 기술을 추가했다’가 완료 조건은 아니야.
