# 학습 순서: 기능 수보다 독립적으로 다룰 수 있는 범위

이 순서는 추천안이야. 졸업 연월, 학기 일정, 지원 회사가 확인되지 않았으므로 월별 마감이나 취업 보장 수준을 정하지 않았어. [진단 과제](02-diagnostics.md)를 한 개씩 수행하고, 결과에 따라 필요한 부분만 선택하면 돼.

## 무엇을 완료로 볼까

한 능력마다 아래 상태를 기록해. 총점을 내거나 신입 합격선으로 사용하지 않아.

| 상태 | 확인된 증거 |
|---|---|
| 아직 확인 안 함 | 설명이나 코드를 평가하지 않음. 부족하다고 판정하지 않음 |
| 안내받아 수행 | 예시 또는 구체적인 수정 지시를 따라 완성 |
| 스스로 수행 | 요구사항을 읽고 구현·검증. 공식 문서나 API 설명 참고는 허용 |
| 다른 상황에 적용 | 이름·조건이 달라진 문제에서 설계와 검증을 다시 수행 |

설명을 잘했어도 구현 증거가 없으면 별도로 적어. 실패했다면 ‘JPA를 못함’ 대신 ‘자바 목록 변경과 DB 외래키 변경을 구분하지 못함’처럼 막힌 단위를 남겨.

## 1단계 — 한 기능의 의미와 상태를 코드로 옮기기

**목표:** 빈 클래스부터 전부 만드는 속도보다, 요구사항을 객체의 책임과 상태 변화로 바꾸는 경험.

현재 library의 다음 주제는 대출 생성이야. 이미 작성한 필드와 관계를 사용하되, 한 대출이 한 회원의 여러 책 묶음이라는 뜻을 유지해. 먼저 생성 시 필요한 값과 날짜 계산을 다루고, 이후 개별 반납을 연결해.

확인할 결과:
- 입력 전후에 어떤 객체의 상태가 달라지는지 설명할 수 있어.
- 날짜와 조건을 고정해서 성공·거절 사례를 직접 확인할 수 있어.
- 같은 규칙을 다른 객체 이름으로 제시해도 책임을 배치할 수 있어.

Java에서 필요한 재료는 생성자, 객체 참조, 컬렉션, 예외, 날짜 API야. 이미 아는 문법은 반복 수강하지 말고 실제로 막힌 부분만 공식 문서에서 확인해.

**넘어갈 기준:** 정상 사례 하나뿐 아니라 규칙을 어기는 사례 하나를 스스로 만들고 검증한다. 구현 방식을 설명할 수 있지만 확인 방법을 못 정한다면 작은 도메인 테스트부터 연습해.

## 2단계 — 객체와 DB 사이에서 실제로 무슨 일이 일어나는지 확인하기

**목표:** 매핑 애노테이션을 붙인 결과를 DB 저장·조회로 설명.

작은 관계 하나에서 시작해. 누가 외래키를 관리하는지, 자바 객체 양쪽 참조가 일치하는지, 저장 후 다시 읽었을 때 무엇이 남는지 확인해. 화면에 같은 값이 보였다는 것만으로 DB 저장을 증명하지는 않아.

확인할 결과:
- 목록 타입이 정하는 상대 클래스와, `mappedBy`가 가리키는 그 클래스 안의 필드를 구분해.
- 테이블에 어떤 외래키 값이 기록돼야 하는지 예측해.
- SQL과 재조회 결과를 비교하고, 예상과 다르면 원인을 좁혀.

**넘어갈 기준:** 관계의 반대편 목록만 변경한 경우와 외래키를 관리하는 참조를 변경한 경우를 실제 결과로 비교한다. 양방향 객체 일관성, 영속성 전이, DB의 외래키 제약은 별개의 문제로 설명한다.

## 3단계 — 여러 변경의 성공과 실패를 함께 다루기

**목표:** 대출 기록과 도서 상태처럼 함께 성공해야 하는 변경을 안전하게 처리.

한 단계가 실패했을 때 남으면 안 되는 데이터를 먼저 적어. 그다음 실제 트랜잭션 경계와 예외 전달을 확인해. ‘메서드에 애노테이션이 있으니 안전하다’는 결론에서 멈추지 않아.

확인할 결과:
- 일부 작업 뒤 실패를 재현하고, 작업 전후 DB 상태를 비교해.
- 테스트가 만든 외부 트랜잭션 때문에 서비스 경계의 문제가 가려지지 않았는지 확인해.
- API 입력 오류, 도메인 규칙 위반, 서버 내부 오류를 구분해.

기본 롤백 규칙은 [공식 자료](05-reference-map.md)에서 확인해. 트랜잭션 하나만으로 동시 요청까지 안전하다고 결론 내리지 않아.

**넘어갈 기준:** 정상 저장, 예상된 거절, 작업 도중 실패 후 상태를 구분해 검증하고 설명한다.

## 4단계 — 요구 변경과 조회 비용 다루기

**목표:** 동작하는 코드에 작은 변경을 주도적으로 적용.

처음에는 부분 반납처럼 합의한 요구를 구현하고, 이후 정렬·페이지 단위 조회 등 하나만 선택해. 한 번에 새 인증·결제·메시지 시스템을 붙이지 않아.

확인할 결과:
- 바뀌어야 하는 코드와 영향을 받지 않아야 하는 동작을 적어.
- 기존 성공·실패 동작을 유지하면서 새 요구를 검증해.
- 조회 성능을 다룬다면 데이터 수, 실행 SQL, 실행 계획 또는 측정 시간을 함께 기록해.

**넘어갈 기준:** AI가 수정 위치를 모두 지정하지 않아도 변경 범위를 찾고, 테스트나 재현 절차로 결과를 확인한다.

## 5단계 — 실제 실행 환경과 사람에게 전달하기

**목표:** 내 IDE 밖에서 기능이 동작하고, 다른 사람이 이해하고 사용할 수 있게 하기.

대표 프로젝트 하나를 골라 좁은 핵심 범위를 끝내. 실행 설정을 분리하고 DB·앱 기동, 로그 확인, 오류 재현 절차를 작성해. 공개 배포나 유료 자원은 실제 단계에서 별도로 범위를 정해.

기회가 되면 학교 프로젝트나 인턴에서 API 계약, Git 변경 리뷰, 충돌 해결, 피드백 반영을 경험해. 혼자 준비하는 동안에는 다른 사람이 README만 보고 실행 가능한지 확인받을 수 있어.

**넘어갈 기준:** 다른 환경에서 재현되는 실행 절차, 사람에게 받은 피드백과 반영 내역, 실제 문제 해결 사례가 남는다.

## 병행할 공부

| 분야 | 프로젝트와 연결하는 방법 | 별도로 확인할 것 |
|---|---|---|
| Java | 객체 상태, 컬렉션 선택, 예외 경계, 날짜·시간 | 객체 동일성/동등성, 제네릭, 런타임 기본 개념 |
| DB·SQL | 조인, 집계, 무결성, 트랜잭션을 직접 실행 | 실행 계획·인덱스, 격리와 락의 기본 원리 |
| HTTP·네트워크 | 요청/응답, 상태 코드, 타임아웃을 실제로 관찰 | TCP·HTTP 흐름, 프로세스/스레드와 I/O |
| 코딩테스트 | 지원 회사 유형에 맞는 제한시간 문제 | 과거 티어나 풀이 수만으로 현재 상태를 확정하지 않음 |
| 취업 자료 | [사례 한 장](templates/case-study.md)을 실제 증거로 작성 | 목표 공고, 본인 기여, 질문에 대한 설명 |

## 다음 단계를 정하는 규칙

- 이미 스스로 수행한 CRUD는 새로운 도메인마다 전부 반복하지 않아도 돼. 필요한 기반 코드만 준비하고 아직 확인하지 못한 능력에 시간을 써.
- 시도한 과제에서 두 번 비슷하게 막히면 주제를 즉시 바꾸지 말고, 막힌 개념의 작은 실험 하나로 좁혀.
- 학습 자료를 다 읽는 것이 완료 조건은 아니야. 코드·SQL·테스트·설명 중 무엇을 남겼는지가 기준이야.
- 한 흐름을 깊게 다뤘으면 [다른 실험](04-next-experiments.md)에서 전이 여부를 확인해. 기존 시스템으로 돌아가 한 기능을 개선하는 것도 다음 경험이 될 수 있어.
