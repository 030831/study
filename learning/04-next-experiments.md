# library 다음에 해볼 경험

아래는 전부 완성해야 하는 프로젝트 목록이 아니야. [진단 결과](02-diagnostics.md)에서 확인된 필요에 맞춰 **하나만** 선택해. 새 주제라도 회원·상품 CRUD를 매번 처음부터 반복할 필요는 없어.

여기서 확정하는 것은 후보 과제의 행동 요구사항이야. 도메인 클래스, 테이블, 구현 순서는 네가 제안하고 검토해. 모든 후보는 아직 착수하지 않았어.

## 고르는 기준

| 확인하고 싶은 능력 | 우선 후보 |
|---|---|
| 기존 코드에서 영향 범위를 찾아 수정 | 이전 쇼핑몰의 취소 흐름 개선 |
| 날짜·시간과 여러 조건을 규칙으로 표현 | 회의실 예약 |
| DB 밖의 작업과 실패·재실행을 구분 | 자료 가져오기 작업 |

동시 요청은 각 후보의 기본 흐름이 확인된 뒤 필요할 때 추가해. 새로운 기술을 쓴 개수로 평가하지 않아.

## 후보 A — 이전 쇼핑몰에서 작은 요구 변경 수행

**목표:** 낯선 프로젝트를 새로 만드는 대신, 복잡해진 기존 코드에서 한 기능의 경계를 다시 잡기.

시작 전에 해당 저장소의 최신 소스와 테스트를 다시 확인해. [경험 비교](01-evidence.md)는 특정 커밋의 기록이지 영구적인 현재 상태가 아니야.

첫 범위:
- 주문 취소 기능 한 경로만 선택한다.
- 현재 취소가 바꾸는 주문 상태, 재고, 결제 금액을 코드에서 추적한다.
- 해당 항목들이 실제로 연결돼 있는지 확인하고, 없는 기능은 있다고 가정하지 않는다.
- ‘취소 가능한 항목과 불가능한 항목이 섞였을 때 어떻게 처리할 것인가’ 같은 변경 하나를 선택한다. 구현 전에 전부 거절/일부 처리 중 정책을 분명히 적는다.
- 수정 전 동작과 수정 후 기대 동작을 같은 입력으로 비교한다.

완료 증거:
- 요청부터 변경된 데이터까지 이어지는 실제 파일 목록.
- 정상·거절·중간 실패 중 해당 변경에 중요한 사례의 테스트 또는 재현 절차.
- 변경한 범위와 건드리지 않은 범위를 설명한 짧은 기록.

보류: 결제대행사 신규 연결, 인증 전면 개편, 프런트엔드 전체 완성. 준비 없이 기존 저장소 전체를 고치지 않아.

**이 후보가 맞는 때:** 작은 기능은 만들 수 있지만 기존 시스템에서 어디를 고칠지 찾기 어려울 때.

## 후보 B — 회의실 예약의 시간 겹침

**목표:** 단순 참/거짓 상태로는 표현하기 어려운 시간 규칙을 코드와 조회로 풀기.

첫 범위:
- 미리 등록된 회의실과 사용자로 예약한다. 회원가입 기능은 요구하지 않는다.
- 예약 시작 시각은 종료 시각보다 앞서야 한다.
- 한 회의실의 유효한 예약끼리는 시간이 겹치면 안 된다.
- 10:00~11:00과 11:00~12:00은 함께 허용한다. 한 예약이 다른 예약 전체를 포함하면 거절한다.
- 취소된 예약은 시간을 차지하지 않는다. 취소 기록은 남긴다.
- 첫 실험에서는 한 서비스 시간대를 정하고 기록한다. 여러 시간대·반복 예약은 후속 요구로 남긴다.

완료 증거:
- 겹침의 경계 사례를 본인이 먼저 제시한다.
- 정상 요청, 포함 관계, 경계가 맞닿는 예약, 취소 후 재예약을 검증한다.
- 애플리케이션 판정과 DB 조회 조건이 같은 의미인지 설명한다.

후속 실험 하나: 기본 흐름이 확인되면 같은 방/시간에 동시에 요청하여 중복 예약 가능성을 직접 검증해. 락이나 격리 수준은 관찰한 문제를 바탕으로 고르고, 단순히 트랜잭션을 붙였다는 이유로 안전하다고 결론 내리지 않아.

보류: 캘린더 UI, 정기 예약, 알림, 조직별 권한, 결제.

**이 후보가 맞는 때:** 관계 매핑 이후 조건을 정확하게 정의하고 경계 사례를 검증하는 경험이 필요할 때.

## 후보 C — 파일에서 자료를 가져오는 작업

**목표:** 요청 한 번의 성공을 넘어 처리 상태·오류·재실행을 다루기.

첫 범위:
- 로컬에 준비한 소규모 UTF-8 CSV 파일을 입력받아 외부 식별자, 제목, 분류를 저장한다. 실제 개인정보를 쓰지 않는다.
- 입력 행은 생성하거나, 같은 외부 식별자가 이미 있으면 사전에 정한 규칙으로 갱신한다.
- 첫 버전은 동기 처리로 시작한다. 별도 큐나 배치 프레임워크가 필수는 아니다.
- 잘못된 행이 하나라도 있으면 해당 가져오기 전체를 거절한다. 실패한 행 번호와 이유를 알려준다.
- 같은 파일을 다시 처리해도 중복 행이 생기지 않아야 한다.

완료 증거:
- 정상 파일, 중복 외부 식별자, 중간 행 오류, 재실행의 전후 DB 상태.
- 파일 읽기 오류와 검증 실패, DB 저장 실패를 구분한 재현 기록.

후속 실험 하나: 일부 행만 처리한 뒤 재시작하거나, 요청과 작업 실행을 분리해야 하는 요구를 추가한다. 저장 단위·재시작 지점·처리 상태를 다시 설계해. 외부 파일이나 알림 전송은 DB 롤백과 별개라는 점을 검증할 기회로 삼아.

성능을 공부할 때의 별도 후보: 데이터 수를 늘려 처리 시간과 메모리 사용을 측정한다. 첫 버전의 완료 조건으로 요구하지 않는다.

보류: 임의 사용자 파일 업로드 공개 서비스, 분산 작업 큐, 대규모 데이터 플랫폼.

**이 후보가 맞는 때:** CRUD와 트랜잭션 이후 실패한 작업을 다시 실행하는 경험이 필요할 때.

## 다음 프로젝트로 이동하기 전

현재 프로젝트가 몇 퍼센트 완성됐는지보다 아래를 확인해.

1. 내가 구현한 핵심 기능 하나를 자료 없이 흐름부터 설명할 수 있는가?
2. 실제로 재현하고 수정한 문제 또는 설계 결정을 근거와 함께 남겼는가?
3. 다음 후보에서 확인하려는 새로운 능력을 한 문장으로 말할 수 있는가?

세 번째가 불분명하면 주제만 바뀐 같은 CRUD가 되기 쉬워. 한 기능을 더 깊게 확인하거나 기존 코드의 작은 변경을 선택해도 돼.
