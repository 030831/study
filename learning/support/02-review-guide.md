# 진단 리뷰 가이드 — 풀이 뒤에 확인하기

[문제 파일](../02-diagnostics.md) · [단계별 힌트](02-hints.md)

이 문서는 정답 코드를 제공하지 않아. 어떤 동작과 반례를 확인해야 하는지, 결과를 어디까지 해석할 수 있는지 설명해. 튜터는 사용자가 풀기 전에 전체 해설을 대화에 붙여 넣지 않아.

**현재 관찰:** 2026-09-07 소스에는 도서 등록·조회 흐름과 `Member`, `Loan`, `LoanItem`, `Book` 매핑이 있어. `Loan`에는 필드만 있고 대출 생성자·서비스는 아직 없어. 이후 미션에서 이런 기능을 이미 구현한 것으로 가정하지 않아. 이 문서를 작성하며 앱 실행이나 학생의 독립 구현 능력을 검증한 것은 아니야.

## 공통 리뷰 방법

1. 사용자가 어떤 업무 사실을 표현하려 했는지 먼저 읽어.
2. 실제 코드가 나타내는 동작과 비교해. 의도와 코드가 다르면 **그 차이 한 곳을 구체적으로 보여줘.**
3. 개념 오해인지, 알고 있지만 표현을 놓친 것인지, 실행 환경이 막힌 것인지 구분해.
4. 수정 이유를 설명한 뒤 이번에 바꿀 범위를 하나로 정해. 다음 기능·리팩터링·새 테스트 과제를 한꺼번에 쌓지 않아.

파일을 이동해서 설명할 때는 “먼저 Member.java”, “이제 Loan.java”처럼 전환을 분리해. 서로 다른 파일의 필드를 붙여 쓴 표만 보여주고 사용자가 연결을 이해했다고 가정하지 않아.

다음은 독립성과 별개로 기록할 증거야. 합산 점수나 합격선은 만들지 않아.

| 관찰 축 | 기록할 근거 |
|---|---|
| 요구 이해 | 사용자가 정의한 규칙과 요청 전후 상태 |
| 변경 위치 | 본인이 찾은 파일, 메서드, 이유 |
| 구현 | 직접 작성한 변경과 사용한 도움 |
| 검증 | 재현 입력, 실제 출력·DB 상태, 기대와 다른 결과 |
| 변경 대응 | 기존 답을 보지 않고 작은 조건 변경을 반영한 증거 |

각 축은 `아직 관찰하지 않음`, `설명 또는 가설만 있음`, `도움을 받아 실행 확인`, `문서 참조로 직접 실행 확인`, `새 조건에도 직접 적용 확인`처럼 사실로 적어. 모든 축을 억지로 한 등급에 맞추지 않아. 문법 검색이나 공식 문서 열람을 독립성 실패로 보지 않고, AI가 설계·구현을 제공한 범위는 따로 표시해.

## D1. 요청 추적의 확인점

현재 소스에서 없는 숫자 ID는 도서 서비스의 조회에서 발견되고, 사용자 정의 예외가 던져지며, 공통 처리기가 그 예외를 HTTP 응답으로 바꿔. 정확한 메서드·본문은 리뷰 시 현재 파일을 다시 확인해.

리뷰에서 볼 것은 다음이야.

- 성공 경로와 실패 경로를 실제 메서드로 구분했는가?
- 없는 숫자 ID와 숫자로 바꿀 수 없는 문자열이 같은 경로라고 단정하지 않았는가?
- JSON 실패 본문 요구를 저장 로직 변경과 혼동하지 않았는가?
- 실행한 결과와 소스만 보고 예측한 결과를 구분했는가?

`abc` 입력의 기본 상태 코드를 외우는 것은 목표가 아니야. 현재 설정·예외 처리에 따른 실제 결과를 확인해야 해. 프레임워크 단계에서 막히면 해당 예외 처리나 변환 과정만 공식 문서로 확인해도 돼.

문제에서는 구현을 요구하지 않았으므로 계획이 타당하다는 이유로 ‘독립 구현 완료’라고 기록하면 안 돼. 작은 변경을 실제 작성하는 단계는 이후 별도로 선택해.

## D2. 업무 기록과 관계의 확인점

제시한 사건이 끝났을 때 필요한 기록은 회원 2명, 책 3권, 대출 묶음 3건, 대출도서 기록 4건이야. 민지의 첫 묶음에는 A와 B, 두 번째 묶음에는 C, 준호의 묶음에는 A가 포함돼. 과거 A 기록에만 반납일이 있고, 준호의 새 A 기록은 아직 반납 전이야.

`LoanItem`은 회원과 대출 사이를 연결하는 객체가 아니라 **한 번의 대출에 포함된 특정 도서의 기록**이라는 정의와 대응해야 해. 사용자가 다른 정의로 이해했다면 매핑 문자열부터 고치지 말고 기록 한 건의 의미부터 맞춰봐.

`Member.java`를 읽을 때 목록 원소는 `Loan`이야. 이 단계에서는 어느 엔티티 목록인지만 확인해.

이제 `Loan.java`에서 `member` 필드를 확인해. 이 필드가 이 대출의 회원을 참조하고, 현재 코드에서는 `member_id` 외래키를 매핑해.

다시 `Member.java`로 돌아오면 `mappedBy = "member"`는 위의 **Loan 안에 선언된 필드 이름**을 지정한 거야. `Member` 클래스를 주인으로 지정한 것으로 설명하지 않아. 양방향 관계의 `mappedBy`는 소유 측 관계 필드나 프로퍼티를 가리킨다는 것이 공식 정의야. [Jakarta Persistence OneToMany API](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/onetomany)

**반례:** 목록 쪽만 변경하고 소유 측 참조를 설정하지 않은 상태, 참조는 설정했지만 새 기록을 저장할 경로가 없는 상태를 구분할 수 있는가? 관계의 소유와 저장 전파는 별개야. 지금 아직 생성·저장 동작이 없다면 이 반례는 설명 단계로 남기고 실행 확인을 요구하지 않아. 실행 가능한 시점에 DB 재조회로 확인해. [Jakarta Persistence 명세](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2)

애노테이션 문자열을 맞힌 것만으로 도메인 모델을 이해했다고 평가하지 않아. 새로운 사건에서도 기록 수와 연결을 직접 정할 수 있는지 봐.

## D3. 대출의 원자성을 확인하는 기준

핵심 규칙은 한 요청의 성공 또는 실패가 관련 데이터 전체에 일관되게 반영되는 것이야. 정상 요청에서는 대출 묶음 한 건과 입력한 서로 다른 책 수만큼의 항목이 생기고, 그 책들의 상태가 대출 중이 돼야 해.

검증에 포함할 사례:

- 서로 다른 두 권 정상 대출: 기록과 대상 책 상태를 DB에서 확인.
- 이미 대출 중인 책이 포함된 요청: 나머지 책 상태와 대출 기록 수가 이전과 같음.
- 없는 회원·도서, 빈 목록, 중복 ID: 합의한 실패 계약과 데이터 불변을 확인.
- 저장 작업 도중 실패: 이번 요청의 대출·항목·책 상태 변경이 남지 않음.
- 월말을 넘는 고정 날짜: 2026-09-25 기준이면 반납예정일은 2026-10-09.

테스트용 실패를 만드는 방법은 단일 정답이 아니야. 테스트에서 저장 의존성의 실패를 제어하거나 DB 제약 실패를 재현할 수 있어. 단, 서비스를 통째로 가짜 객체로 바꿔 예외만 던지는 테스트로 실제 원자성을 증명할 수는 없어. 실제 쓰기가 이뤄지는 경로를 거치게 하고, 기능 코드에 영구적인 ‘실패 테스트 전용 API’를 만들 필요는 없어.

**거짓 확신을 피할 점:** 모든 입력을 먼저 검사해 쓰기 없이 종료된 실패, 예외 발생만 확인한 테스트, 테스트 프레임워크의 마지막 자동 롤백은 각각 서비스의 쓰기 중 롤백을 증명하지 않아. 서비스 트랜잭션이 끝난 뒤 별도 조회로 남은 데이터를 확인해. SQL 실행이 미뤄질 수 있는 ORM 검증에서는 flush와 실제 트랜잭션 완료를 구분해. [Spring 테스트 트랜잭션 공식 문서](https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/tx.html)

`@Transactional`이 있다는 사실만 읽고 검증 완료로 판정하지 않아. 실제로 적용되는 호출 경계와 예외 정책을 확인해. Spring 기본 롤백 대상과 checked exception 설정을 구분해야 하지만 관련 설정을 모두 암기하게 할 필요는 없어. [Spring 롤백 공식 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)

현재 매핑에 cascade가 없다는 이유만으로 바로 `ALL`을 권하지 않아. 어떤 객체가 다른 객체의 생명주기를 관리하는지, 명시 저장과 전파 중 무엇을 선택했는지 근거를 봐. 성공 사례는 정상 저장 흐름의 증거야. 쓰기 도중 실패 후 별도 재조회까지 확인해야 해당 실패 시나리오의 원자성을 뒷받침할 수 있어. 어느 쪽도 동시 중복 대출 방지의 증거는 아니야.

## D4. 기록에 대한 요청과 현재 책 상태를 구분하는 기준

문제의 네 요청을 처리한 결과:

- 민지의 A 대출도서 기록은 최초 반납일을 유지한다.
- 민지의 B 기록은 아직 반납 전이고 B는 대출 중이다.
- 준호의 A 기록은 아직 반납 전이고 A도 대출 중이다.
- 민지의 옛 반납 요청을 다시 처리해도 준호의 대출 상태는 변하지 않는다.

반납 대상을 책 ID만으로 처리하는지, 특정 대출 기록을 식별하는지 확인해. 재요청이 이미 반납된 기록을 뜻하는데 매번 책 상태를 대출 가능으로 덮어쓰면 마지막 규칙이 깨질 수 있어. 사용자가 직접 이 반례를 찾아 설명했다면 의미 있는 증거야.

선택한 계약은 ‘같은 기록의 재요청은 첫 반납일을 유지하며 성공’이므로, 첫 반납 날짜와 다른 날짜로 재요청해도 기록이 유지되는지 봐. 존재하지 않는 기록, 대출 이전 날짜의 최초 반납은 실패해야 해. 과거 반납의 재요청과 새 반납의 날짜 검증 우선순위도 계약과 맞춰야 해.

객체 단위 테스트는 상태 전이의 증거야. 반납 기록과 도서 상태가 함께 저장되는지는 실제 저장 검증으로 보완해. 모든 반례를 한 세션에 구현하도록 재촉하지 말고 현재 실패한 규칙 하나부터 수정해.

## D5. 새 업무로 전이됐는지 확인하는 기준

정원 1인 사례에서는 민지의 최초 신청이 유효할 때 준호의 신청은 실패해야 해. 민지가 취소하면 자리가 생기고 준호의 새 신청이 가능해져. 민지의 취소된 신청 이력은 남아 있어야 해.

고정된 클래스명이나 엔티티 개수로 채점하지 않아. 확인할 것은 다음이야.

- 회원·행사·신청 시도 또는 기록이 나타내는 사실을 구분했는가?
- 같은 회원이 같은 행사에 다시 신청해도 과거 취소 이력을 잃지 않는가?
- 현재 유효 신청 중복 방지와 과거 신청 기록 보관을 함께 만족하는가?
- 정원 판단과 신청 생성, 취소와 자리 회복의 관계를 설명하는가?
- 이전 도서관의 묶음 객체를 실제 요구 없이 추가하지 않았는가?

신청 기록에서 `(회원, 행사)`를 무조건 유니크로 만들면 취소 이력을 여러 행으로 남기며 재신청하려는 설계와 충돌할 수 있어. 반대로 유니크가 없으면 중복을 어떻게 막는지 질문이 남아. 테이블 하나를 정답으로 강요하기보다 선택한 저장 모델이 요구사항을 만족하는 반례를 직접 확인하게 해.

과거 취소와 새 신청을 서로 다른 기록으로 두는 방식, 현재 상태와 별도 이력을 나누는 방식 등은 비용이 달라. 사용자 선택을 듣기 전에 전부 나열할 필요는 없어. 어떤 방식을 쓰더라도 요구사항과 실제 기록이 일치해야 해.

Java 단위 테스트까지만 했다면 ‘핵심 규칙의 순차 동작’이 확인된 거야. DB 일관성과 동시성까지 검증했다고 확대하지 않아.

## D6. 동시성의 증거를 확인하는 기준

확인해야 할 것은 정원 1일 때 두 요청이 경합해도 **하나만 성공하고 유효한 저장 기록도 하나만 남는지**야. 트랜잭션을 붙였다는 설명, 락 이름을 말한 것, `sleep`을 길게 준 코드 자체가 증거는 아니야.

검증 기록에는 최소한 DB 종류와 격리 수준, 각 요청의 독립 트랜잭션, 실제 겹치도록 조절한 지점, 최종 상태를 확인한 시점이 있어야 해. 모르는 환경 값은 추측하지 않고 미확인으로 적어. 스레드별로 별도 작업이 실행되도록 준비한 데이터가 이미 커밋됐는지 확인하고, 작업 종료 후 새 트랜잭션으로 결과를 읽어.

대안의 선택은 예를 들어 다음 판단을 포함할 수 있어: 충돌 감지 후 실패·재시도를 허용할지, 공통 데이터 접근을 직렬화할지, DB 조건부 변경으로 규칙을 지킬지. 사용자가 선택한 방법이 어떤 데이터 경쟁을 막는지 설명하면 돼. 하나의 잠금 방식을 모든 업무에 필수로 적용하게 하지는 않아. JPA의 잠금 의미는 공식 명세를 기준으로 확인하고, 실제 DB 동작도 별도로 검증해. [Jakarta Persistence 명세 3.5절 잠금과 동시성](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2)

한 번 통과했다고 모든 순서에서 안전하다는 증명은 아니야. 대표적인 겹침을 재현한 테스트와 설계상의 보장 근거를 함께 보고, 검증하지 않은 환경까지 안전하다고 적지 않아.

## D7. 조회 측정과 개선의 확인점

현재 구현을 측정하기 전에 N+1이나 인덱스 문제라고 판정하지 않아. 응답에 어떤 데이터가 필요한지와 실제 조회가 실행하는 SQL을 함께 봐.

검증 기록에 포함할 것:

- 대출 수와 항목 수를 구분한 준비 데이터. 20건 중 최근 10건의 예상 ID.
- 같은 대출일에 대한 보조 정렬 기준과 결과의 안정성.
- 데이터 준비 쿼리를 제외한 조회 요청의 SQL 또는 쿼리 수.
- 객체 캐시와 새 조회 여부, 첫 실행과 반복 실행의 구분 등 비교 조건.
- 조회 변경 전후 같은 결과를 반환한다는 증거.

대출 한 건에 항목이 많을 때 조인으로 생긴 행 수를 대출 건수와 혼동하지 않아야 해. 조회 최적화 후 페이지 범위나 중복 여부가 달라지면 성능 개선으로 완료할 수 없어.

Spring Data JPA의 쿼리 정의나 EntityGraph 등은 후보를 조사하는 근거가 될 수 있지만, SQL 수를 무조건 1로 만들라는 규칙은 아니야. [Spring Data JPA 쿼리 공식 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html)

부하가 작고 비교 근거가 없으면 ‘성능 90% 개선’ 같은 문구를 쓰지 않아. 개선할 이유를 발견하지 못한 결론도 측정 조건과 한계를 설명했다면 유효한 판단이야.

## 튜터의 다음 응답 형식

사용자에게는 선택한 미션의 결과만 짧게 돌려줘.

```text
확인한 것: 실제 코드·실행 결과에서 확인한 사실.
아직 불분명한 것: 틀렸다고 단정하기 전에 확인할 전제 또는 빠진 증거.
이번에 보완할 한 가지: 왜 필요한지와 사용자가 직접 해볼 범위.
```

미션 답변이 길어졌다는 이유로 이해했다고 가정하거나, 질문을 했다는 이유로 실력이 없다고 판단하지 않아. 바로 답을 반복하기보다 사용자가 어떤 대상·관계를 다르게 생각하는지 먼저 확인해.
