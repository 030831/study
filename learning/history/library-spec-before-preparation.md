## 3. 도메인 규칙 (확정 — 논쟁 없음)

| # | 규칙 |
|---|---|
| R1 | 대출 기간은 **14일** |
| R2 | 이미 대출 중인 책은 대출 불가 |
| R3 | 한 회원이 동시에 빌릴 수 있는 책은 **최대 5권** |
| R4 | 반납예정일이 지나고 아직 반납 안 됐으면 **연체** |
| R5 | 연체일수 = 오늘 − 반납예정일 |
| R6 | 반납하면 그 책은 다시 대출 가능 |
| R7 | 연체료는 계산하지 않음 (범위 밖) |

## 4. 엔티티 (3개)

**Book (도서)**
- 식별자 (PK, 자동 생성)
- 제목 변수
- 저자 변수
- ISBN 변수 (**유니크**)
- 현재 대출 가능 여부를 나타내는 변수

**Member (회원)**
- 식별자 (PK, 자동 생성)
- 이름 변수
- 이메일 변수 (**유니크**)
- 가입일시 변수

**Loan (대출 기록)**
- 식별자 (PK, 자동 생성)
- 도서 참조 (Book 으로의 다대일 연관)
- 회원 참조 (Member 로의 다대일 연관)
- 대출일 변수
- 반납예정일 변수 (대출일 + 14일)
- 실제 반납일 변수 (아직 반납 전이면 비어 있음)
- 대출 상태 변수 (Enum: 대출중 / 반납완료)

## 5. API

| 기능 | 메서드 | 경로 | 요청 본문 | 응답 |
|---|---|---|---|---|
| 도서 등록 | POST | `/books` | 제목·저자·ISBN | 생성된 도서 |
| 도서 전체 조회 | GET | `/books` | - | 도서 목록 |
| 도서 단건 조회 | GET | `/books/{id}` | - | 도서 |
| 회원 등록 | POST | `/members` | 이름·이메일 | 생성된 회원 |
| 대출 | POST | `/loans` | 회원 식별자·도서 식별자 | 대출 기록 |
| 반납 | PATCH | `/loans/{id}/return` | - | 대출 기록 |
| 회원별 대출 목록 | GET | `/members/{id}/loans` | - | 대출 목록 |
| 연체 목록 | GET | `/loans/overdue` | - | 대출 목록 (연체일수 포함) |

## 6. 예외

- 도서 없음 / 회원 없음 / 대출 기록 없음
- 이미 대출 중인 도서 (R2 위반)
- 대출 한도 초과 (R3 위반)
- 이미 반납된 대출을 또 반납 (중복 반납)
- `@RestControllerAdvice` 전역 핸들러로 HTTP 상태 매핑

## 7. 마일스톤

각 마일스톤은 **엔티티 → Repository → Service → Controller → 테스트** 한 세트를 끝까지 관통한다.
(층별로 쌓지 말 것. 세로로 하나씩 완성해야 동작하는 걸 계속 확인할 수 있다.)

- [ ] **M1 — Book**: 엔티티 + Repository + 등록/전체조회/단건조회 API + 테스트
- [ ] **M2 — Member**: 엔티티 + Repository + 등록 API + 테스트
- [ ] **M3 — Loan 엔티티**: 연관관계 매핑 + Repository. `@DataJpaTest` 로 저장/조회 확인
- [ ] **M4 — 대출 API**: R2, R3 검증 포함 + 테스트 (성공 / 이미 대출중 / 한도 초과)
- [ ] **M5 — 반납 API**: 상태 변경 + 도서 대출 가능 복구 + 테스트
- [ ] **M6 — 조회**: 회원별 대출 목록, 연체 목록(연체일수 계산)
- [ ] **M7 — 예외 핸들러**: `@RestControllerAdvice` + 상태 코드 매핑
- [ ] **M8 — MySQL 전환**

### 2026-09-06 — 서비스 계층 입력 방식 결정 (확정, 재논의 금지)

**결정(최종): 3번 — 서비스 전용 Command 객체를 `record` 로 만들고, 요청 DTO의 `toCommand()` 로 변환해 넘긴다.**

검토한 세 안:
1. 웹 요청 DTO를 서비스까지 전달 — 계층이 섞임
2. 파라미터 나열 — 사용자가 이미 쓰던 방식
3. **서비스 전용 Command 객체 — 채택**

최종 판단 기준: 1번은 계층이 섞이므로 탈락. 2번과 3번은 계층 분리를 동일하게 만족하고 기술적 우열이 없다.
(3번의 근거로 든 "인자 순서 안전성"은 성립하지 않음 — Command 생성자도 위치 인자라 순서 위험을 제거하지 못하고
호출부에서 생성자로 옮길 뿐이다.) **둘이 대등할 때는 사용자가 안 써본 쪽을 고른다** — 이 프로젝트의 목적이 학습이기 때문.
2번은 사용자가 이전 쇼핑몰에서 이미 쓴 방식이라 새로 배울 게 없다.

참고 — 3번의 근거로 "인자 순서 안전성"을 들었으나, Command 생성자도 위치 인자라 순서를 바꿔 써도 컴파일된다.
즉 순서 위험을 제거하는 게 아니라 호출부에서 생성자로 옮길 뿐이다. 계층 분리는 2번도 동일하게 만족하므로
클래스만 하나 더 늘어난다.
