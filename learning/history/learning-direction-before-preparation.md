- Plus 사용량을 고려해 품질을 유지하면서 간결하게 답하고 불필요한 조회를 줄인다.

## 현재까지 확인한 library 경험

사용자가 직접 구현했고, 코드 리뷰와 사용자 요청 결과로 확인한 범위:
- 도서 등록: 정상 요청 201, 생성된 ID와 도서 정보 반환.
- 빈 제목 등록: 사용자가 400 응답을 확인했다고 보고.
- 도서 단건 조회: 정상 ID 200.
- 없는 도서: BookNotFoundException 및 공통 예외 처리기로 404와 메시지 반환.
- 도서 전체 조회: 빈 배열과 등록 후 도서 배열 모두 200, 스크린샷 확인.
- 서비스 입력은 제목/저자/ISBN 개별 파라미터로 받는다.
- 응답 변환은 ResponseBook(Book) 생성자로 모았다. Command 또는 정적 from 메서드 도입은 필수로 보지 않는다.
- 회원 엔티티 과제를 제안한 직후 사용자가 학습 방향 논의를 요청했다. 회원 구현 완료로 간주하지 않는다.
- 자동 테스트, 전체 빌드, 미구현 기능까지 검증 완료한 것은 아니다.

- library를 버리거나 계속하기 전에, 이전에 막힌 실제 장면을 하나 확인한다.
- 계속한다면 기능 수를 늘리는 것보다 대출/반납 같은 한 흐름에서 사용자가 설명·구현·변경할 수 있는지를 확인하는 방안을 검토한다. 아직 구현 과제로 확정하지 않았다.
- 이전 프로젝트의 한 기능을 좁혀 다시 이해하고 구현하는 방안도 후보이며, 선택은 사용자 답변 후 함께 검토한다.

## 사용자 후속 답변

- AI 도움 없이 완전히 혼자 해보고 싶지만 진입장벽이 높게 느껴진다.
- 약간의 AI 도움으로 진행해도 규모가 커지면 혼자 감당하기 어려워졌다고 설명했다.
- 엔티티/DTO/Repository/Service를 만드는 작업은 여러 번 해봐서 괜찮다.
- 그 반복이 취업 준비에 실제로 도움이 되는지 의문을 갖고 있다.
- 특정 실패 기능이나 원인은 아직 밝혀지지 않았다. 이 답변만으로 JPA/트랜잭션 지식 부족 등으로 단정하지 않는다.

## 다음 방향 제안 — 사용자 합의 전

- 계층별 CRUD 반복을 기본 학습 과제로 계속 내는 방식은 중단한다.
- library를 당장 폐기하기보다 기존 뼈대를 활용해 대출/반납 한 흐름에 집중하는 방안을 우선 추천한다.
- 기능 범위를 좁히는 이유는 품질을 낮추기 위해서가 아니라, 한 기능의 설계·구현·실패 처리·검증을 사용자가 직접 감당할 수 있게 하기 위해서다.
- 대출 불가/반납 후 재대출 같은 규칙, 변경의 원자성, 이를 확인하는 최소 테스트는 해당 단계에서 다룰 후보다. 동시성·인증·배포 등을 한꺼번에 추가하지 않는다.
- 튜터는 먼저 행동 요구사항과 완료 조건을 제공한다. 파일/메서드별 지시를 기본으로 하지 않고 사용자가 실제로 막힌 부분에만 도움을 준다.
- 문법·의존성·공식 문서 등 참고 재료와, 설계/구현을 대신하는 도움을 구분한다. 문서 참조까지 금지하는 암기 시험으로 만들지 않는다.
- 성과는 API 수보다, 기존 완성 코드를 복사하지 않고 기능 흐름을 설명·구현하고 작은 요구 변경에 대응할 수 있는지로 확인한다.
- 이는 사용자 답변에 따른 제안이며, 프로젝트 지속과 구체적 다음 과제는 아직 확정하지 않았다.

## 2026-09-06 — 신입 백엔드 취업 준비의 기준

사용자 질문: 간단한 library 프로젝트 완성만으로 취업에 도움이 된다고 보기 어렵다. 신입 백엔드 개발자가 되기 위해 실제로 무엇을 준비해야 하는가?

튜터의 제안이며, 사용자의 세부 일정/목표 회사와 합의한 최종 계획은 아니다.

- 현재 수준의 도서 CRUD만으로 차별화된 지원 자료가 된다고 보기는 어렵다. library는 독립 구현을 확인할 연습 대상으로 활용할 수 있으며, 반드시 최종 포트폴리오로 확장할 필요는 없다.
- 준비를 네 축으로 나눈다: (1) Java/DB/HTTP/Spring/JPA 원리를 코드와 연결하는 기본기, (2) 요구사항에서 구현·디버깅·변경까지 진행하는 능력, (3) 배포·운영 및 실제 사람과 협업한 경험, (4) 본인 기여와 판단을 설명하는 이력서/면접 및 목표 회사의 전형 준비.
- 기본기를 전부 끝낸 뒤 프로젝트를 시작하는 방식 대신, 한 기능에서 만난 문제와 관련 원리를 함께 공부한다. CS와 코딩테스트는 프로젝트만으로 대체하지 않는다.

## 대출 구조 논의 — 최신 합의

- 학습을 진행하기로 했고, 다음 경험은 사용자가 설계하고 구현하는 대출 기능이다.
- 처음 제시했던 한 권 단위 대출에서 사용자가 여러 권을 묶는 대출을 제안했고, 이를 다루기로 했다.
- 회원 1:N 대출, 대출 1:N 대출도서, 도서 1:N 대출도서로 구성한다. 대출도서는 LoanItem으로 부른다.
- 대출은 LoanItem 목록을 가진다. 한 번에 빌린 여러 권 중 일부만 먼저 반납할 수 있다.
- Loan의 대출일은 여러 권을 함께 빌린 날이다. 개별 책의 실제 반납일은 LoanItem에 둔다.
- Loan 전체의 실제 반납일을 중복 저장하지 않는 데 사용자가 동의했다. 전체 반납은 미반납 항목들을 처리한다. 전체 반납 완료일이 필요하면 모든 항목 반납 여부 확인 후 마지막 반납일로 계산할 수 있다.
- 사용자는 도서 대출 상태 변경과 대출 기록 저장을 하나의 트랜잭션으로 관리해야 한다고 답했다. 실패 시 별도 취소 작업보다 함께 롤백한다는 설명을 제공했다.
- 이 합의는 기존 library/docs/SPEC.md의 한 권 단위 Loan 및 상태 필드 설계보다 우선한다.
- 실제 파일 확인: Book 존재, Loan은 식별자만 작성된 상태. Member와 LoanItem은 아직 없다.
- 다음 과제: 엔티티의 관계와 날짜를 코드로 표현한다. 이번 14일 공통 대출 기간에서는 Loan에 대출일/반납예정일, LoanItem에 실제 반납일을 두도록 제안한다. 연장 정책은 범위에 포함하지 않았다.
- Member는 이번 관계 구현에 필요한 식별자/이름만 준비하고 회원 CRUD로 학습을 되돌리지 않는다. 기능 코드와 매핑은 사용자가 작성한다.

## 관계 리뷰에서 발생한 오해와 안내 보완

- 사용자는 완성된 도메인 모델을 옮겨 적는 중이 아니라, 스스로 설계하면서 배우고 있다. 과거에 맞는 설명을 했거나 동의했어도 이후 구현에서 같은 개념을 정확히 이해하고 있다고 단정하지 않는다.
- 최초 제안은 Book과 Loan의 N:M을 LoanItem으로 푸는 것이었고 타당했다. 이후 사용자는 Member와 Loan의 N:M을 LoanItem으로 푼 것으로 설명했다. 최초 제안 자체가 틀렸다고 기록하지 않는다.
- 실제 리뷰한 코드: LoanItem은 Loan과 Book을 참조했고, Member는 List<LoanItem>과 mappedBy="loanItem_id"를 두었다. Loan.loanItems에도 같은 잘못된 mappedBy가 있었다.
- 튜터는 리스트 타입과 mappedBy 수정을 지적했지만, 사용자가 어떤 두 엔티티의 관계를 풀었다고 생각하는지부터 확인하지 않았다. 이후 올바른 구조의 예시를 반복해도 사용자의 출발 전제가 달라 설명이 전달되지 않았다.
- 리뷰에서는 먼저 사용자가 의도한 관계, 현재 코드가 표현하는 연결, 둘의 불일치를 구체적으로 짚는다. 문법 오류와 도메인 이해의 차이를 구분한다. 사용자의 의도가 불명확하면 해당 관계에 한정해 확인한다.
- 이번에는 'LoanItem에 Member 참조가 없고 Loan과 Book 참조가 있다. 그런데 Member는 LoanItem 목록을 갖고 있다'는 실제 코드의 어긋남을 먼저 설명했어야 한다.
- 사용자가 반복해서 왜냐고 물으면 정답 구조를 더 반복하기보다 내가 잘못 가정한 이해나 용어부터 점검한다. 예시나 그림 자체를 금지하는 규칙으로 확대하지 않는다.
- 사용자의 지적을 '매핑을 전혀 리뷰하지 않았다'로 단순화하지 않는다. 문제는 도메인 전제의 차이를 놓치고 수정 지시를 먼저 한 설명 방식이다.
- Member/Loan/LoanItem은 사용자가 작성했고 리뷰 중이다. 관계 수정 완료나 개념 이해 완료로 간주하지 않는다. 날짜 필드 등 나머지 검토는 보류 중이다.

## 엔티티 매핑 수정 리뷰 완료

- 최신 소스에서 Member.loans의 mappedBy="member", Loan.loanItems의 mappedBy="loan", Book.loanItems의 mappedBy="book"을 확인했다. JoinColumn 이름은 member_id, loan_id, book_id이며 대응하는 필드에 배치돼 있다.
- 세 목록 모두 ArrayList로 초기화했다. Loan에 LocalDate loanDate/dueDate, LoanItem에 LocalDate returnedDate가 있고 반납 전 null을 허용한다.
- 소스 리뷰 범위에서 요청한 수정은 완료됐다. 애플리케이션 시작이나 DB 저장으로 매핑을 실행 검증한 상태는 아니다.
- mappedBy 설명은 '주인이 누구인가'라는 축약 대신 '상대 엔티티에서 이 관계를 관리하는 필드 이름을 지정하며, 이쪽은 반대편임을 나타낸다'로 한다. 목록의 제네릭이 상대 엔티티를 정하고 mappedBy 문자열은 그 엔티티 내부의 필드를 가리킨다고 구분해서 설명한다.
- 다음은 대출 생성 시 회원/대출일/반납예정일을 갖추는 동작을 사용자가 작성하는 단계로 안내한다. 조회된 회원과 기준 날짜를 입력받게 하면 날짜를 고정한 검증이 가능하다. 생성자 추가 시 JPA용 기본 생성자를 유지하는 점을 함께 안내한다.
